# App Workflow

This document maps the end-to-end workflow of BCTN from data ingestion to day-to-day app usage.

## Overview

Two SQLite databases are involved:

- Names DB (read-only): generated by `bctn-ingest`, then baked into the Docker image or used locally.
- App DB (read-write): created at runtime by the backend; stores accounts, sessions, swipes, matches, and settings.

## Data Workflow (names DB)

```mermaid
flowchart TD
  A[Raw sources: database_source] --> B[bctn-ingest ingest]
  B --> C[Names DB: bctn.sqlite]
  C --> D[Wikidata cache: wikidata_cache.json]
  C --> E[Variant edges: wikidata]
  C --> F[Variant edges: ensemble]
  E --> G[bctn-ingest variants materialize]
  F --> G
  G --> H[Materialized tables for fast API reads]
  H --> I[Backend uses names DB read-only]
```

### Typical commands

- Full rebuild: `bctn-ingest rebuild-all` (recommended)
- If you run steps manually: ensure you run `bctn-ingest variants materialize` at the end

## Runtime Workflow (backend + PWA)

```mermaid
flowchart TD
  U[User opens app] --> S[Backend serves PWA static files]
  S --> L[Frontend calls GET /api/me]
  L -->|401| LI[Login screen]
  L -->|200| BOOT[Bootstrap client state]
  LI --> POSTLOGIN[POST /api/auth/login]
  POSTLOGIN -->|Set-Cookie session| BOOT
  BOOT --> USERS[GET /api/users]
  BOOT --> SETTINGS[GET /api/settings]
  BOOT --> FEED[GET /api/feed/batch]
  FEED --> DECK[Deck: show top card]
  DECK --> SWIPE[POST /api/swipes]
  SWIPE -->|match_created true| MATCHANIM[Match animation]
  SWIPE --> NEXT[GET /api/feed/next]
  NEXT --> DECK
```

## Auth and session lifecycle

```mermaid
sequenceDiagram
  participant C as Client (PWA)
  participant B as Backend
  participant DB as App DB (SQLite)

  C->>B: POST /api/auth/login (username, password)
  B->>DB: Verify user + insert session (expires_at)
  B-->>C: Set-Cookie bctn_session (HttpOnly, SameSite=Lax, Secure if enabled)

  C->>B: GET /api/me (cookie)
  B->>DB: Load session by hash and update last_seen_at
  alt Near expiry
    B->>DB: Extend expires_at
    B-->>C: Refresh Set-Cookie (sliding session)
  else Not near expiry
    B-->>C: 200 OK
  end

  C->>B: POST /api/auth/logout
  B->>DB: Delete session
  B-->>C: Clear cookie
```

## Card model and matching

The app presents either:

- a group card (variant group), or
- a concept card (fallback when no group exists).

Swipes and matches are keyed by `card_key`.

```mermaid
flowchart TD
  CARD[Card key] --> SW1[User A swipe: like/superlike/nope]
  CARD --> SW2[User B swipe: like/superlike/nope]
  SW1 --> CHECK{Both users liked/superliked?}
  SW2 --> CHECK
  CHECK -->|yes| MATCH[Create match for card_key]
  CHECK -->|no| NOMATCH[No match]
```

## Partner-priority cards

If your partner liked or super-liked a card, that card is surfaced on top of your deck regardless of your current filters, and it stays until you swipe it.

```mermaid
flowchart TD
  A[Load feed candidates] --> B{Partner has liked/superliked unseen cards?}
  B -->|yes| P[Serve partner-priority card]
  B -->|no| F[Serve next filtered card]
  P --> S[User swipes it]
  F --> S
  S --> N[Next card]
```

## Card details view (front/back)

```mermaid
flowchart TD
  FRONT[Front of card] --> TAP[Tap card]

  BACK --> DETAILS[Fetch details if needed: GET /api/card/:card_key]

```

## Admin workflow (two accounts)

The system enforces a hard cap of two total users (DB trigger).

```mermaid
flowchart TD
  ADMIN[Admin user] --> A[Open Admin page]
  A --> LIST[GET /api/admin/users]
  A --> CREATE[POST /api/admin/users]
  A --> UPDATE[PATCH /api/admin/users/:id]
  A --> DELETE[DELETE /api/admin/users/:id]
  CREATE --> RULES[New user must change password on first login]
  DELETE --> SAFE[Cannot delete last active user or last admin]
```
